Ce qu'elle fait, comment elle est construite, pourquoi elle est rapide, et comment on l'a mesuré.

Accroche (30 s). « ng-table est une bibliothèque Angular qui affiche et manipule des tableaux de données, de dix lignes à un million. Je vais vous montrer ce qu'elle sait faire, puis ouvrir le capot : l'architecture, les algorithmes qui la rendent rapide, les Web Workers, et la façon dont on l'a comparée à AG Grid. »

Plan en 4 temps : 1. le fonctionnel, 2. l'architecture du code, 3. la performance (rendu, tri, filtres, live, worker), 4. la mesure (benchmark) et la qualité.

Durée visée : 30 à 40 minutes, démo comprise. Les notes de chaque diapositive (touche N) contiennent ce qu'il faut dire et les réponses aux questions probables.

Message : la bibliothèque est déclarative. On décrit les colonnes (un identifiant, un en-tête, une fonction valueAccessor qui lit la valeur dans la ligne), on donne les lignes, et le composant fait le reste.

Technique : Angular 22, composants standalone, signals, sans zone.js (zoneless). Typée de bout en bout : NgTableColumn<T> connaît le type de la ligne.

Dépendances : @angular/cdk (moteur de tableau CdkTable) et rien d'autre. Material a été retiré : paginateur, cases à cocher, menus, listes déroulantes, info-bulles et icônes sont maison. Avantage : pas de thème Material imposé, paquet plus léger.

Installation : ng add @sbourahla/ng-table (schéma qui ajoute le CDK et, avec --locale, la langue).

Taille du code : environ 19 800 lignes de source dans la bibliothèque, dont 5 700 pour le composant principal ; le reste est découpé en modules purs.

Deux modes de données à bien distinguer :

  • Local (dataMode='local') : toutes les lignes sont dans le navigateur ; la table trie, filtre, pagine elle-même.
  • Distant (dataMode='remote') : le serveur trie et filtre. La table émet (remoteQueryChange) avec la requête (tri, filtres, page) et affiche ce qu'on lui renvoie. Variante « par blocs » : défilement continu sur des millions de lignes serveur.

Motif contrôlé / non contrôlé : chaque état (tri, filtres, sélection, lignes dépliées…) peut être laissé à la table, ou piloté par l'application avec une entrée et une sortie. C'est le même motif que les formulaires.

Dernière nouveauté (4.0.1) : en maître / détail, dès qu'un detailRowTemplate est fourni, une colonne de 44 px porte un chevron par ligne (clavier, aria-expanded). [detailRowToggleButton]="false" le retire.

Message clé : la séparation entre « calcul » et « affichage ». Les fonctions de tri, de filtre, de fusion live ne connaissent pas Angular. Trois bénéfices : (1) tests unitaires simples et rapides, (2) le même code tourne dans le Web Worker, (3) le composant reste un chef d'orchestre.

Le chemin d'une ligne : elle entre par [rows] ou par une transaction, est rangée par clé dans le RowStore, passe les filtres et la recherche, est triée, éventuellement groupée et paginée ; le défilement virtuel ne garde que la tranche visible ; row-view.ts construit le « modèle de vue » (valeur, texte, classes de chaque cellule) et le gabarit HTML le rend dans une <table cdk-table>.

Pourquoi CdkTable ? Il fournit la sémantique <table>, les colonnes et en-têtes collants. C'est le moteur de mat-table, sans l'habillage Material.

Si on vous demande « pourquoi un composant de 5 700 lignes ? » : il porte toute l'API publique (entrées, sorties, méthodes) et la coordination ; les algorithmes en sont déjà sortis. La suite logique est de continuer à extraire.

Architecture

Signals et zoneless : ne recalculer que le nécessaire

1

Chaque étape est un computed. Le résultat est mémorisé ; il n'est recalculé que si un signal qu'il lit a changé.

2

Changer la sélection ne retrie rien. Le tri dépend des lignes, des filtres et du tri, pas de la sélection.

3

Pas de zone.js. Angular ne revérifie pas tout l'écran à chaque clic ou minuteur : seul ce qui lit un signal modifié est rafraîchi (OnPush).

4

Modèle de vue mis en cache. valueAccessor est appelé une fois par cellule rendue, pas à chaque détection de changements.

// Schéma simplifié du composant
filtered  = computed(() => filtrer(rows(), filters()));
sorted    = computed(() => trier(filtered(), sort()));
window    = computed(() => tranche(sorted(), scrollTop()));
rowViews  = computed(() => vues(window(), colonnes()));

// Défiler : seuls window et rowViews se recalculent.
// Cocher une ligne : aucun des quatre.

Un signal, c'est une valeur qui prévient quand elle change. Un computed est une valeur dérivée : Angular note quels signaux il a lus et ne le recalcule que si l'un d'eux a changé, et seulement quand quelqu'un le relit (paresseux).

Conséquence pour la grille : le graphe de dépendances fait le tri entre ce qui doit être refait et ce qui ne doit pas. Défiler ne refiltre pas. Ouvrir un menu ne reconstruit pas les cellules.

Zoneless : historiquement Angular utilisait zone.js pour intercepter tous les événements et relancer une vérification globale. Sans zone, la vérification est déclenchée par les signaux. Pour une grille qui reçoit des milliers de mises à jour par seconde, c'est décisif.

Le modèle de vue (buildRowViews) : pour chaque ligne rendue et chaque colonne visible, on calcule une fois la valeur, son texte, le texte à copier et le contexte du gabarit. Le gabarit HTML ne fait que lire ce résultat. Avec la virtualisation des colonnes, il n'est calculé que pour les colonnes rendues.

Le code de la diapositive est un schéma : dans le composant réel, filtre et tri passent par l'IncrementalPipeline (diapositive « mode live »).

Performance

Pourquoi une grille devient lente,
et les deux réponses

1. Le DOM

50 000 lignes dans la page, c'est 50 000 <tr> à créer, mesurer et peindre. Réponse : ne rendre que ce qui se voit.

2. Le calcul

Trier un million de lignes avec un comparateur, c'est environ 20 millions de comparaisons. Réponse : changer d'algorithme, et au besoin changer de fil d'exécution.

Transition vers la partie performance. Posez le cadre : deux coûts indépendants.

Le DOM : le navigateur doit créer chaque élément, calculer son style, sa position, puis le peindre. Ce coût est proportionnel au nombre d'éléments à l'écran, pas au nombre de lignes de données, à condition de virtualiser.

Le calcul : un tri par comparaisons coûte n·log₂(n) comparaisons. Pour n = 1 000 000, log₂(n) ≈ 20, donc environ 20 millions d'appels au comparateur, chacun appelant deux fois valueAccessor. C'est ce qui prend plusieurs secondes.

Et le JavaScript n'a qu'un fil pour la page : pendant ces secondes, rien d'autre ne répond. D'où le Web Worker, qu'on verra plus loin.

Performance · rendu

Défilement virtuel : une vingtaine de lignes dans le DOM

Le temps de rendu ne dépend plus du nombre total de lignes.

premier = floor(scrollTop / hauteurLigne)
visibles = ceil(hauteurZone / hauteurLigne)
début = premier − 8
fin   = premier + visibles + 8
  • Deux lignes d'espacement donnent à la barre de défilement la hauteur de la liste complète.
  • Les hauteurs sont mesurées : une ligne plus haute (détail déplié, texte sur plusieurs lignes) est retenue, et les positions se lisent dans un arbre de sous-totaux.
  • Au-delà de 15 millions de pixels, la barre est comprimée : les navigateurs plafonnent la hauteur d'un élément.
  • Même principe en largeur : [virtualColumns], marge de 300 px.

Principe : on ne crée que les lignes de la zone visible, plus 8 lignes de marge de chaque côté pour que le défilement reste fluide et que le focus clavier ait toujours une ligne voisine. Au-dessus et au-dessous, une ligne vide dont la hauteur vaut « nombre de lignes non rendues × hauteur de ligne ».

La formule est dans virtual-window.ts (computeVirtualRange) : une division et quelques bornes. Fonction pure, testée seule.

Hauteurs différentes (ajout récent) : la formule ci-dessus vaut tant que toutes les lignes ont la même hauteur. Dès qu'une ligne rendue s'en écarte, la grille retient l'écart et calcule les positions avec un arbre de Fenwick (des sous-totaux : une position se lit en une vingtaine d'opérations sur un million de lignes, row-heights.ts). Limites : une ligne jamais affichée n'est qu'estimée ; les mesures sont oubliées quand la liste change ; pas en mode blocs ni quand la barre est comprimée.

La compression (question fréquente des experts) : Chrome plafonne un élément à environ 33 millions de px, Firefox à 17,9 millions. Un million de lignes de 48 px fait 48 millions de px : la fin serait inatteignable. Au-delà de 15 millions, la position de la barre est convertie proportionnellement en position réelle (scrollRatio). AG Grid fait la même chose.

Colonnes : avec 100 colonnes, seules celles de la zone visible (plus 300 px de marge) sont rendues ; les colonnes épinglées le sont toujours.

Modèle serveur par blocs (si on vous le demande) : même fenêtre, mais les lignes viennent du serveur par blocs de 100. Cache de 50 blocs, les moins récemment affichés sont oubliés (LRU), 2 requêtes simultanées au plus ; un numéro de « génération » fait ignorer les réponses arrivées après un changement de tri ou de filtre.

Performance · algorithme

Tri par base (radix) : trier sans comparer

On ne compare plus les lignes deux à deux : on les range dans des cases d'après les chiffres de leur clé.

1

Une colonne de nombres par niveau de tri. valueAccessor est appelé une fois par ligne ; nombre, date, booléen et rang du texte deviennent un Float64Array.

2

On lit la clé morceau par morceau, en commençant par la fin, comme on lirait d'abord les unités, puis les dizaines, puis les centaines.

3

À chaque passe, on pose les lignes dans des cases selon ce morceau, puis on les ramasse dans l'ordre des cases. Quatre passes suffisent.

4

On ne bouscule jamais l'ordre d'arrivée dans une case (tri « stable ») : c'est ce qui permet de trier sur plusieurs colonnes.

Colonne aux types mélangés ou date invalide : retour automatique au tri classique. Un test compare les deux tris sur des données aléatoires.

Analogie : pour ranger un paquet de cartes numérotées, on peut les comparer deux à deux (tri classique), ou les distribuer en tas selon le dernier chiffre, ramasser les tas dans l'ordre, puis recommencer avec le chiffre précédent. Après le dernier chiffre, le paquet est trié. C'est le tri par base, version « chiffre de poids faible d'abord » (LSD).

Ici le « chiffre » fait 16 bits (65 536 valeurs possibles) et un nombre JavaScript fait 64 bits, donc 4 passes. Chaque passe : (a) un histogramme, combien de lignes par case ; (b) une somme cumulée, où commence chaque case ; (c) recopie des indices à leur place. Tout se fait sur des Uint32Array d'indices : on ne déplace jamais les objets lignes.

Pourquoi l'astuce des bits ? Les nombres à virgule (IEEE 754) ne se trient pas directement comme des entiers à cause du signe. En inversant le bit de signe des positifs et tous les bits des négatifs, l'ordre des entiers obtenus est exactement l'ordre des nombres.

Stabilité : deux lignes de même clé gardent leur ordre relatif. C'est ce qui permet le tri multi-niveaux : trier d'abord par montant, puis par client ; le second tri ne dérange pas l'ordre des montants à client égal.

Les vides valent +∞ : toujours en dernier, dans les deux sens (le sens décroissant multiplie les valeurs par −1 avant, pas les vides).

Fichier : fast-sort.ts, fonctions sortKeyColumn, radixSortByKeys, buildSortOrder. Gain mesuré : tri numérique d'un million de lignes passé de 2,7 s à 0,35 – 0,65 s (chargement compris).

Performance · algorithme

Trier du texte : le ramener à des nombres

Le tri de texte respecte la langue (Intl.Collator) : casse ignorée, « item 2 » avant « item 10 ». C'est correct, mais lent.

Peu de valeurs distinctes (statut, pays…)

On trie seulement les valeurs distinctes avec le collateur, on leur donne un rang, et chaque ligne reçoit le rang de sa valeur.

Un million de lignes, 5 statuts : 5 textes à trier, puis un tri par base sur les rangs.

Beaucoup de valeurs distinctes (références…)

Pour du texte ASCII, la table construit une clé de tri en octets : comparer les octets donne le même ordre que le collateur. Ces clés sont triées par base.

La clé est vérifiée contre le collateur sur un corpus avant usage ; au moindre écart, retour au collateur.

Le choix se fait sur un échantillon des 2 000 premières valeurs (seuil : 25 % de valeurs distinctes). Texte accentué ou non ASCII : le collateur, comme avant. Le résultat est toujours celui du collateur ; seul le chemin change.

Pourquoi le texte est difficile : on ne peut pas trier par code de caractère (« Z » passerait avant « a », « é » très loin). Intl.Collator applique les règles de la langue, mais un appel à compare est coûteux, et il en faut 20 millions.

Idée 1, les rangs : si la colonne a peu de valeurs différentes, on ne trie que ces valeurs. Chaque ligne se voit attribuer un nombre (le rang) et on retombe sur le tri par base de la diapositive précédente.

Idée 2, les clés en octets (ascii-collation.ts) : pour chaque caractère ASCII imprimable, on mesure son rang avec le collateur lui-même, et on écrit une clé où les suites de chiffres sont comparées par valeur et la casse ignorée. Comparer deux clés octet par octet équivaut alors à collator.compare.

Le point à souligner, la sûreté : cette équivalence n'est pas supposée, elle est vérifiée à l'exécution sur un corpus d'essai avant la première utilisation. Si le navigateur a un collateur aux règles différentes, la vérification échoue et on garde le collateur. On ne sacrifie jamais l'exactitude à la vitesse.

Chiffres : tri de texte sur un million de valeurs distinctes : 6,4 s avant, 1,0 – 2,4 s maintenant. C'est le scénario où l'écart avec AG Grid est le plus faible (×1,7) : le texte reste le cas difficile.

Performance · algorithme

Filtres compilés : lire la saisie une fois, pas un million

Avant : interpréter pour chaque ligne

pour chaque ligne :
  lire ">5000"            // expression régulière
  convertir "5000" en nombre
  comparer la cellule

Maintenant : compiler, puis appliquer

const test = compiler(">5000");
// test = (valeur) => valeur > 5000
pour chaque ligne :
  test(cellule)

Ce qui est compilé

>5000, 10..50, Validée,Annulée, périodes de dates, opérateurs de texte.

Recherche globale

Le texte normalisé de chaque ligne est calculé une fois et mis en cache : ensuite quelques dizaines de ms par frappe sur un million de lignes.

Garantie

Un test compare le filtre compilé à l'ancien sur plus de 12 000 couples valeur / saisie.

« Compiler » ici veut dire : transformer une fois le texte saisi par l'utilisateur en une fonction prête à l'emploi. Le terme vient des compilateurs, mais il n'y a pas de génération de code : on fabrique une fermeture (closure) qui a déjà en mémoire le seuil, les bornes ou l'ensemble de valeurs.

Exemple : pour 10..50, on découpe et on convertit les bornes une fois ; la fonction retournée ne fait plus que cellule >= 10 && cellule <= 50. Pour une liste Validée,Annulée, on construit un ensemble (Set) et chaque ligne fait une recherche en temps constant.

Pourquoi c'était lent : l'ancien code relisait la saisie (expression régulière, découpage, passage en minuscules) pour chaque ligne. Sur un million de lignes, c'était l'essentiel du temps du filtre.

Plusieurs filtres : compileFilters assemble les fonctions des colonnes filtrées en un seul prédicat ; une ligne est rejetée dès le premier filtre qui échoue.

Résultat : filtres passés de 0,5 – 1,1 s à 0,2 – 0,45 s sur un million de lignes. Face à AG Grid : ×23 sur le filtre texte.

Fichier : filter-compile.ts.

Performance · mémoire de travail

Se souvenir : ne pas relire ce qu'on a déjà lu

Trois ajouts récents (branche feat/stockage-colonnes) : ils accélèrent la deuxième action, pas la première.

Colonnes de tri gardées

Les valeurs de tri d'une colonne sont lues une fois, puis gardées (8 octets par ligne). Inverser le sens, filtrer en restant trié : plus de relecture.

Dictionnaire

Colonne à valeurs répétées (statut, client) : le filtre est testé une fois par valeur distincte, pas une fois par ligne.

Filtre plus strict

« dup » → « dupo » : seules les lignes déjà retenues sont retestées, sans retrier.

Idée commune : la partie chère d'un tri ou d'un filtre est de lire la valeur dans chaque ligne et, pour du texte, de la classer. Tant que les données ne changent pas, ce travail peut servir plusieurs fois.

Colonnes de tri (column-store.ts) : deux tableaux de nombres par colonne. Le sens décroissant relit les mêmes chiffres « en complément » ; les cellules vides sont mises de côté pour rester en fin de liste. 8 colonnes au plus, vidées dès que les lignes changent (nouveau tableau, transaction).

Dictionnaire : liste des valeurs distinctes + un numéro par ligne (2 octets). Limité à 4 096 valeurs distinctes ; une colonne de références uniques reste filtrée ligne par ligne.

Filtre plus strict : la grille ne prend le raccourci que si elle est sûre (saisie de texte prolongée, filtre ajouté, mot ajouté à la recherche). « 1 » puis « 12 » sur des nombres n'est pas plus strict : calcul complet. Vérifié sur 3 000 couples de filtres aléatoires.

Honnêteté : le premier tri ne gagne rien, donc le benchmark face à AG Grid (qui ne mesure que des premiers tris) ne change pas. Les chiffres du tableau viennent d'un test Node, médiane de 5 passages : ordre de grandeur, pas valeur exacte. Mode live : le cache est vidé à chaque transaction, ni gain ni perte.

Cellules prêtes à l'emploi : cell: {type: 'badge' | 'avatar' | 'link' | 'progress' | 'rating' | 'dataBar' | 'colorScale'} sur une colonne, sans gabarit. À montrer en démonstration : page Nouveautés de la démo, section 1 (les sections 2 à 5 montrent le surlignage, le tri en mémoire avec son temps, les hauteurs variables et les blocs annulés).

Confort visuel : lignes qui glissent au changement de tri ([animateRows]), en-tête du groupe en cours collé en haut ([stickyGroupHeaders]), repères des lignes sélectionnées ou signalées le long de la barre de défilement ([scrollMarkers]). Tout est désactivé par défaut.

Où le montrer : page Nouveautés de la démo, sept sections avec un encadré « À essayer » chacune ; la section 3 affiche le temps de chaque tri, ce qui rend visible le « premier tri lent, inversion rapide ».

Aussi ajouté : surlignage du texte trouvé ([highlightSearch]), état vide avec bouton « réinitialiser les filtres », feuille de style d'impression ; modèle par blocs : demandes annulables (AbortSignal) et chargement d'avance ([prefetchBlocks]).

Performance · temps réel

Mode live : ne retraiter que ce qui a changé

Cotations, supervision, suivi de commandes : des milliers de mises à jour par seconde sur un tableau déjà trié et filtré.

1

Transactions. applyTransaction({add, update, remove}) : on envoie seulement les lignes touchées, retrouvées par leur clé.

2

Regroupement. applyTransactionAsync accumule pendant 50 ms : un seul recalcul et un seul rendu par lot.

3

Fusion. Chaque ligne modifiée est refiltrée, retirée de son ancienne place et insérée à la nouvelle par recherche dichotomique dans le résultat déjà trié.

4

Surbrillance. Vert si le nombre monte, rouge s'il baisse, avec un repère ▲ ▼ pour les daltoniens.

Pour k lignes modifiées sur nCoût
Tout retriern · log n
Fusion incrémentalek · log n

k = 1 000, n = 1 000 000 : environ 20 000 comparaisons au lieu de 20 millions. Le reste est de la copie native de tranches de tableau.

Changer un filtre, le tri ou les colonnes recalcule tout : la fusion ne sert que lorsque seules les données changent.

Deux classes pures dans live-rows.ts :

  • RowStore : les lignes rangées par clé (rowKeyAccessor, sinon id). Il retient quelles clés ont changé depuis la dernière lecture et l'ancienne version de chaque ligne modifiée.
  • IncrementalPipeline : le résultat filtré et trié. Si la configuration (filtres, tri, colonnes) n'a pas changé, il appelle merge ; sinon rebuild.

La recherche dichotomique : dans une liste triée, on trouve une position en coupant l'intervalle en deux à chaque essai : 20 essais pour un million de lignes. On la fait deux fois par ligne modifiée : pour trouver l'ancienne place, puis la nouvelle.

Les totaux (barre d'état) sont tenus à jour de la même façon : on retire l'ancienne valeur de la somme, on ajoute la nouvelle ; une resynchronisation complète périodique évite la dérive d'arrondi.

Données immuables : le mode live marche aussi sans transactions. À chaque nouveau tableau [rows], la table compare clé par clé ; seules les lignes dont l'objet a changé sont retraitées. Il faut donc créer un nouvel objet quand une ligne change ({...ligne, prix}).

Démo : la page Live envoie jusqu'à 50 000 mises à jour par seconde sur 100 000 instruments, avec le compteur d'images par seconde. Mesure : un lot de 1 000 mises à jour sur un million de lignes coûte une dizaine de ms, rendu compris.

Web Workers

Un Web Worker, c'est quoi

La page n'a qu'un fil d'exécution : pendant qu'il trie, il ne peut ni peindre, ni réagir au clavier. Un worker est un second fil, fourni par le navigateur.

  • Les clics, la saisie, le défilement

Web Worker

  • Du JavaScript, en parallèle
  • Pas de DOM, pas de window
  • Sa propre mémoire : rien n'est partagé

On ne lui passe pas de fonctions

Seulement des données, copiées à l'envoi (« clonage structuré »).

Copier coûte cher

Copier un million d'objets bloque le fil principal, exactement ce qu'on voulait éviter.

Sauf les tampons « transférables »

Un ArrayBuffer change de propriétaire sans copie : c'est instantané.

Le modèle d'exécution du navigateur : une boucle d'événements, sur un seul fil. Elle traite une tâche à la fois : un clic, un minuteur, le calcul d'une image. Une tâche de 2 secondes (un tri) gèle tout : pas de défilement, pas de curseur qui clignote, pas d'animation.

Le worker est un autre fil avec sa propre boucle d'événements. On communique par messages : worker.postMessage(données) d'un côté, onmessage de l'autre. Aucune variable n'est partagée, donc pas de verrous ni de conflits d'accès.

Les trois contraintes qui dictent la conception de la diapositive suivante :

  • Pas de fonctions : or nos colonnes sont définies par des fonctions (valueAccessor). On ne peut pas envoyer « les lignes et la façon de les lire ».
  • La copie : par défaut un message est cloné. Un million d'objets, c'est des centaines de ms sur le fil principal.
  • Le transfert : un ArrayBuffer (la mémoire derrière un Float64Array) peut être « transféré » : le worker en devient propriétaire, l'émetteur ne peut plus y toucher, et rien n'est copié.

Si on vous demande SharedArrayBuffer : il permet de partager la mémoire, mais exige des en-têtes HTTP d'isolation (COOP / COEP) qu'une bibliothèque ne peut pas imposer à l'application. Le transfert suffit ici.

Web Workers

Comment ng-table s'en sert

[workerCompute]="true" : tri, filtres et recherche globale partent dans le worker à partir de 100 000 lignes.

1. Extraireles colonnes de valeurs utiles : résultats de valueAccessor
→
2. Empaqueternombres en Float64Array, textes en un seul tampon UTF-8
→
3. Transférersans copie, une seule fois par jeu de données
→
4. Calculermêmes modules : filtres compilés, tri par base
→
5. Recevoirl'ordre des lignes retenues : un Uint32Array d'indices

Pendant le calcul

L'ancien résultat reste affiché, la table reste utilisable (aria-busy). Une demande plus récente remplace celle en cours : chaque calcul porte un numéro.

Aucune configuration

Le worker est livré dans la bibliothèque : une source de 12 Ko, empaquetée par esbuild et chargée dans un Blob.

Repli automatique

Si le worker échoue (politique de sécurité, plantage), la table revient au fil principal. [computeWorkerFactory] permet de fournir le sien.

La réponse aux trois contraintes : on n'envoie ni les lignes ni les fonctions. Le fil principal applique lui-même valueAccessor et envoie le résultat, colonne par colonne. Seules les colonnes nécessaires partent : celles qui sont filtrées, triées, ou cherchées.

Empaquetage (packValues) : une colonne entièrement numérique devient un Float64Array. Une colonne de textes devient une seule grande chaîne (séparateur : caractère nul) encodée en UTF-8 dans un Uint8Array. Les deux sont transférables. Copier un million de chaînes une par une coûtait ~560 ms ; le tampon unique ~155 ms.

Une seule fois : le client (ComputeWorkerClient) retient quelles colonnes ont déjà été envoyées pour ce jeu de données. Un second tri sur la même colonne n'envoie plus qu'un petit message de réglages.

Dans le worker (WorkerComputeCore) : les « lignes » sont de simples indices 0…n−1. Il applique exactement les mêmes modules que le fil principal (c'est le bénéfice des modules purs), et renvoie un Uint32Array : « affiche la ligne 812, puis la 14, puis… ». Le fil principal reconstitue le tableau trié (20 à 80 ms).

Course entre demandes : l'utilisateur tape vite dans un filtre. Chaque demande a un numéro (job) ; quand une réponse arrive, isLatest(job) dit si elle est encore d'actualité, sinon elle est ignorée.

Livraison : une bibliothèque Angular ne peut pas livrer un fichier worker que l'application empaquetterait. scripts/bundle-worker.mjs empaquette donc le worker en une chaîne de caractères (worker-source.generated.ts) ; à l'exécution on en fait un Blob et une URL. npm run worker:check vérifie en intégration continue que ce fichier généré est à jour.

Web Workers

Le worker ne rend pas le calcul plus rapide

Il le déplace : le calcul dure autant, parfois un peu plus, mais la page ne gèle plus.

Ce qui reste sur le fil principal (1 M de lignes)

Extraire une colonne de nombres≈ 40 ms
Extraire une colonne de textes≈ 155 ms
Reconstituer les lignes triées20 – 80 ms
Le tri lui-même (dans le worker)0,2 – 2,5 s

Quand l'activer

  • Mode local, plusieurs centaines de milliers de lignes
  • Tris de texte et filtres qui figeaient la saisie

Quand s'en passer

  • Flux live : le worker ne reçoit plus que les lignes modifiées, mais retrie tout à chaque lot ; sur des listes moyennes, la fusion du fil principal reste meilleure
  • Données arborescentes, filtre à fonction sur mesure (filterPredicate) : calcul sur le fil principal
  • Petits volumes : le coût du message dépasse le gain

C'est la nuance qui montre qu'on maîtrise le sujet. Un worker n'accélère pas un algorithme. Ce qu'on mesure, c'est le gel : la plus longue période pendant laquelle le fil principal ne répond pas.

Lecture du tableau : sans worker, un tri de texte d'un million de lignes gèle la page 1 à 2,5 s. Avec worker, le gel tombe à l'extraction de la colonne (≈ 155 ms la première fois) puis à la reconstitution (≈ 80 ms) ; les fois suivantes, seulement ≈ 80 ms.

Honnêteté : ces coûts ont été mesurés sous Node sur le poste de développement. Le banc « Calcul en Web Worker » de la page /benchmark mesure le gel avec et sans worker dans le navigateur ; je n'ai pas encore de relevé publié fait dans un Chrome visible. Si la question vient, dites-le tel quel et proposez de le lancer en direct.

Et le live ? Avant, chaque transaction renvoyait toutes les colonnes au worker (relecture du million de lignes sur le fil principal). Depuis l'ajout récent, la grille envoie une retouche : valeurs des lignes modifiées, indices des lignes retirées, lignes ajoutées ; le worker corrige ses colonnes. Il refait ensuite tri et filtre en entier, hors du fil principal. Sur le fil principal, la fusion incrémentale reste imbattable pour 1 000 mises à jour (quelques millisecondes). Le gain de la retouche n'a pas été chronométré dans un navigateur.

Seuil : [workerThreshold], 100 000 lignes par défaut. (computing) émet le début et la fin du calcul pour afficher un indicateur.

Comment la comparaison avec AG Grid a été faite

Page /benchmark de la démo : tout le monde peut la relancer et copier le rapport.

1

Mêmes conditions. Même navigateur, mêmes données générées, une grille à la fois, réglages par défaut des deux côtés.

2

Huit scénarios. Chargement, tri numérique, tri texte, tri sur deux niveaux, filtre texte, filtre numérique, saut à 90 %, lot de 1 000 mises à jour.

3

Le rendu est compté. Le chronomètre va de l'appel à la fin de la deuxième image peinte.

4

Médiane de 5 passages, tri et filtres remis à zéro entre deux scénarios.

// Le cœur de la mesure
const début = performance.now();
scénario.run(grille);            // ex. trier
await imageSuivante();           // requestAnimationFrame
await imageSuivante();           // la 2e : c'est peint
temps.push(performance.now() - début);
// ... 5 fois, puis :
résultat = médiane(temps);

AG Grid Community 34 est installé à part, dans benchmarks/ : il n'est pas livré avec la bibliothèque. Un onglet masqué ne peint pas : la page le détecte et le signale dans le rapport.

Pourquoi « deux images peintes » ? Mesurer seulement le calcul avantagerait une grille qui reporte son rendu à plus tard. requestAnimationFrame appelle une fonction juste avant que le navigateur peigne une image. Après le premier appel, la grille a pu programmer son rendu ; après le second, ce rendu a été peint. On mesure donc ce que l'utilisateur perçoit.

Pourquoi la médiane et pas la moyenne ? Un passage perturbé (ramasse-miettes, autre processus) fausse une moyenne ; la médiane est la valeur du milieu des 5 passages, elle ignore les extrêmes.

Pourquoi une grille à la fois ? Pour qu'elles ne se disputent ni la mémoire ni le processeur. Chaque grille est créée, mesurée, puis détruite.

Remise à zéro : une première version laissait le filtre numérique actif pendant « saut » et « mises à jour ». Les deux dernières lignes étaient faussées (jusqu'à ×105 affiché à tort). C'est corrigé : chaque scénario remet tri et filtres à zéro. Racontez-le : c'est un bon exemple de rigueur de mesure.

Le banc worker utilise une sonde de gel (withFreezeProbe) : pendant l'opération, une boucle relève le plus long intervalle entre deux tours de la boucle d'événements. C'est le gel ressenti.

Deuxième série de mesures, hors navigateur : des tests de performance (PERF_ROWS=1000000 npm run test:ci) rejouent tri, filtre, pivot sur un million de lignes pour suivre les régressions.

Lancer : cd benchmarks && npm install une fois, puis npm start et ouvrir /benchmark. Gardez la fenêtre au premier plan.

Benchmark · lecture

Ce que ces chiffres disent, et ne disent pas

Ce qu'on peut affirmer

  • Sur ce poste, pour ces huit opérations, ng-table est au moins à égalité et souvent 10 à 20 fois plus rapide.
  • Le gain vient d'algorithmes identifiés : tri par base, filtres compilés, fusion incrémentale.
  • L'écart grandit avec le volume.
  • La mesure est reproductible par n'importe qui.

Ce qu'on ne peut pas affirmer

  • « ng-table est 20 fois plus rapide qu'AG Grid » en général : un écart sur le tri numérique ne vaut pas pour toute la grille.
  • Une seule machine, un seul navigateur (Chrome avec une extension Avast).
  • AG Grid aux réglages par défaut : ses options d'optimisation ne sont pas explorées.
  • AG Grid couvre plus de fonctionnalités, notamment en version Enterprise.

Cette diapositive protège votre crédibilité. Un public technique se méfie des benchmarks ; annoncer vous-même les limites désamorce les objections.

Formulation conseillée : « Sur un million de lignes, dans les mêmes conditions, ng-table trie des nombres une vingtaine de fois plus vite et filtre une dizaine à une vingtaine de fois plus vite qu'AG Grid Community avec ses réglages par défaut. Sur le défilement, elles sont à égalité. »

Si on demande « pourquoi AG Grid est plus lent ? » : ne spéculez pas sur son code. Dites ce que vous savez : ng-table utilise un tri spécialisé sans comparateur et des filtres compilés ; AG Grid est une grille plus générale, avec beaucoup plus d'options, dont certaines (transactions asynchrones, tampon de lignes) n'ont pas été activées ici.

Si on demande « pourquoi ne pas utiliser AG Grid alors ? » : ng-table est sous votre contrôle, sans licence Enterprise pour le pivot, le regroupement ou l'export Excel, en français, accessible, et taillée pour Angular moderne (signals, zoneless). AG Grid reste plus riche et plus éprouvé.

Tests d'équivalence

Chaque optimisation est comparée à l'ancienne version sur des données aléatoires : tri par base contre tri classique, filtre compilé contre filtre interprété, clés ASCII contre collateur.

Harnais de test livré

NgTableHarness : les applications testent leur table sans dépendre de son HTML interne.

Fichiers générés vérifiés

theme:check et worker:check échouent si le thème CSS ou la source du worker ne sont pas à jour.

L'idée forte : le test d'équivalence. Quand on remplace un algorithme simple et lent par un algorithme rapide et subtil, le risque est de changer le résultat dans un cas limite. On garde donc l'ancien comme référence et on vérifie sur des milliers de cas aléatoires que les deux donnent exactement la même chose (vides, égalités, négatifs, dates, casse…).

Tests de bout en bout : Playwright pilote un vrai Chromium sur la démo : tri au clavier, menu des colonnes, maître / détail, arabe de droite à gauche. axe-core analyse chaque page et le test échoue à la moindre violation WCAG.

Un exemple de régression attrapée : au survol d'une ligne en mode live, de grandes flèches apparaissaient. Cause : une règle CSS background: (raccourci) remettait à zéro la taille du repère. Corrigé en background-color, avec un test qui échoue sans le correctif.

Intégration continue : GitHub Actions lance lint, tests unitaires, e2e, build, et les vérifications theme:check / worker:check sur chaque pull request.

Accessibilité et thème

Utilisable par tous, habillable par chacun

Accessibilité

  • Sémantique. Vraie <table>, aria-sort, rôle treegrid quand des lignes se déplient, aria-expanded.
  • Virtualisation annoncée. aria-rowcount / aria-colcount : le lecteur d'écran connaît le total, pas seulement ce qui est rendu.
  • Clavier. Navigation cellule par cellule, tri, réordonnancement et redimensionnement des colonnes.
  • Vision. Contraste élevé de Windows, palette vérifiée par simulation de daltonisme, formes en plus des couleurs.
  • Cibles de 24 px, respect de « moins d'animations ».

Thème

  • 38 jetons CSS --ngt-* : couleurs, rayons, hauteurs, police. Un jeton redéfini sur un conteneur s'applique à tout, menus compris.
  • Sombre : [theme]="'dark'", 'auto' ou la classe ngt-dark.
  • Apparence « material » : provideNgTableLook('material'), texte noir, traits noirs, icônes pleines.
  • Textes : tous traduisibles, cinq langues livrées, droite à gauche.

Accessibilité : l'argument, c'est que la virtualisation casse normalement les lecteurs d'écran (ils annonceraient « tableau de 20 lignes »). Avec aria-rowcount et aria-rowindex, ils annoncent « ligne 812 sur 1 000 000 ».

Daltonisme (WCAG 1.4.1) : l'information ne doit pas passer par la couleur seule. La palette des graphiques a été vérifiée par simulation (modèle de Machado, protanopie, deutéranopie, tritanopie) dans color-vision.ts ; les courbes ont des formes de points et des tiretés distincts ; le mode live ajoute ▲ ▼ ◆ à la couleur.

Contraste élevé : règles @media (forced-colors: active) pour que focus, tri actif, sélection restent visibles quand Windows impose ses couleurs.

Limites à dire : pas encore de campagne de test manuelle avec NVDA ou VoiceOver, ni de vérification sur un vrai Windows en contraste élevé ; les traductions es / de / ar mériteraient une relecture par des locuteurs.

Thème : les jetons sont déclarés dans theme.ts ; le CSS du thème sombre est généré à partir de cette table (npm run theme:css). Une seule source de vérité.

Limites

Ce que la bibliothèque ne fait pas encore

À dire avant qu'on vous le demande.

  • Défilement virtuel : hauteurs différentes gérées, mais une ligne jamais affichée n'est qu'estimée ; lignes uniformes supposées en mode blocs et au-delà de 15 M px.
  • Modèle serveur par blocs : pas de regroupement ni de paginateur ; sélection et clavier portent sur les lignes chargées.
  • Colonnes virtuelles : la navigation clavier ne parcourt que les colonnes rendues.
  • Worker : pas pour les arbres ni les filtres à fonction ; en flux live, il retrie tout à chaque lot.
  • Tri de texte non ASCII (accents, arabe…) : chemin du collateur, plus lent que l'ASCII.
  • Mesures : une seule machine ; le gain du worker dans un Chrome visible reste à publier.
  • Accessibilité : audit automatique complet, tests manuels avec lecteurs d'écran à faire.
  • Composant principal volumineux : l'extraction en modules se poursuit.

Posture : une bibliothèque sérieuse connaît ses limites. Chacune de celles-ci est documentée dans le README.

Sur les hauteurs : la grille mesure et mémorise la hauteur des lignes rendues qui s'écartent de la hauteur habituelle. Ce qui reste estimé, ce sont les lignes jamais affichées.

Sur le texte accentué : le résultat est correct, c'est seulement la voie rapide qui ne s'applique pas. Les valeurs peu nombreuses (statuts, pays) restent rapides grâce aux rangs.

Feuille de route (ROADMAP.md) : gardez deux ou trois priorités en tête pour répondre à « et ensuite ? » : tests manuels d'accessibilité, mesures worker en conditions réelles, poursuite du découpage du composant.

Questions probables

Huit questions, huit réponses courtes

Pourquoi ne pas avoir pris AG Grid ?Maîtrise du code, pas de licence pour pivot, regroupement et export Excel, accessibilité et français d'origine, Angular moderne.
Le tri par base donne-t-il le même résultat ?Oui : stable, vides en dernier, et comparé à l'ancien tri sur des données aléatoires. Sinon, repli automatique.
Combien de lignes au maximum ?Un million en mémoire sans difficulté ; au-delà, le modèle serveur par blocs : le navigateur ne garde que 50 blocs.
Le worker accélère-t-il le tri ?Non, il le sort du fil principal : la page reste fluide pendant le calcul.
Et sans Blob (politique de sécurité stricte) ?Repli automatique sur le fil principal, ou worker fourni par [computeWorkerFactory].
Pourquoi sans Material ?Moins de dépendances, pas de thème imposé, paquet plus léger ; une apparence « material » reste disponible.
Le benchmark est-il honnête ?Mêmes données, même navigateur, rendu compté, médiane de 5, réglages par défaut ; une seule machine, et il est relançable par tous.
Compatible avec quel Angular ?Angular 22 et CDK 22 ; composants autonomes, signals, sans zone.js.

Questions plus pointues, pour être prêt :

  • « Pourquoi 16 bits par passe ? » Compromis : 8 bits demanderait 8 passes ; 16 bits en demande 4 avec un histogramme de 65 536 cases qui tient dans le cache du processeur.
  • « Et la mémoire ? » Par niveau de tri : un Float64Array (8 octets par ligne) et quelques Uint32Array (4 octets par ligne). Pour un million de lignes : quelques dizaines de Mo, temporaires.
  • « Les signaux dans valueAccessor ? » Ils sont suivis : si la langue change, le modèle de vue se recalcule.
  • « Tri stable, ça sert à quoi ? » Les lignes égales gardent leur ordre d'arrivée : pas de lignes qui « sautent » entre deux rafraîchissements, et tri multi-niveaux correct.
  • « Sécurité du pivot serveur ? » Les champs sont validés contre une liste blanche côté Spring Boot, jamais injectés tels quels dans la requête.
  • « Rendu côté serveur (SSR) ? » Si vous ne l'avez pas vérifié, dites-le : « je ne l'ai pas testé, je reviens vers vous ».

Règle d'or : si vous ne savez pas, dites « je vérifie et je vous réponds » plutôt que d'improviser.
